# Handoff: две вещи, которые открыл pi 1.0.0 — для отдельной сессии

Записано 2026-10-03, во время перевода семейства плагинов на **pi 1.0.0** (журнал
той сессии — вне этого репозитория). Здесь только то, что относится к
`pi-alibaba-models`, и **ничего из этого не сделано**: это заготовка задачи, а не
отчёт. Причина, по которой пишу: оба пункта — не косметика, но каждый требует
своего решения и своей проверки, а в чужой сессии их трогать нельзя.

Контекст по хосту на момент записи: pi 1.0.0, `@earendil-works/pi-ai` 1.0.0.
Сам форк на 1.0.0 уже переведён: `npm run build`/`npm run test` зелёные,
116 → 119 тестов (коммит `v1.5.3`), провайдеры загружаются.

## 1. `alibaba_tools` — перевести на `exposure: "codemode"`?

**Что измерено.** Инструмент регистрируется без `exposure` (`extensions/alibaba.ts`,
вызов `pi.registerTool({ name: "alibaba_tools", … })`), то есть как `direct`:
`description` + `promptSnippet` + параметры едут в запрос **каждый** ход, хотя
инструмент нужен редко (свежие факты, разбор страниц, sandbox, поиск картинок).

**Что появилось в 1.0.0.** `ToolExposure = "direct" | "model-only" | "codemode" |
"deferred" | "hidden"` (в `pi-coding-agent/dist/core/extensions/types.d.ts`;
документация — `docs/extensions.md`, раздел про Tool exposure). `codemode`:
«callable whenever registered, and listed by the `codemode` tool. Not declared to
the model unless activated explicitly» — то есть инструмент остаётся вызываемым
(в том числе из JS-скриптов через `ctx.executeTool()`), но перестаёт занимать
декларацию, пока его не включат.

**Почему это может быть выгодно.** У этого расширения инструмент тяжёлый по
описанию: `description` — 2 предложения, плюс `promptSnippet`, плюс схема на четыре
действия. В семействе есть чем сравнить: `pi-nvidia-plus` вообще хук-онли, а
расширения без инструментов не платят ничего. Оценка «сколько именно токенов» —
первое, что надо измерить, и это измеряется **до** кода: взять текст декларации,
посчитать токены тем же токенайзером, что у DashScope, и умножить на число ходов в
типовой сессии.

**Риски, которые надо назвать явно.**
- Инструмент перестаёт быть виден модели «просто так»: пользователь, который
  привык, что Qwen сам зовёт `alibaba_tools`, увидит, что больше не зовёт. Лечится
  либо `prepareLoadout()` (динамически возвращать декларацию, когда включён режим
  «хочу sidecar»), либо активацией: `direct` и `model-only` активируются при
  регистрации, остальные нет (`docs/extensions.md`).
- `codemode` требует, чтобы у пользователя был включён сам codemode
  (`defaultTools`, `codemode.mode`). Если у него выключен — инструмент становится
  недостижим **вообще**, и это надо честно написать в README/CHANGELOG, а не
  «тихо» поменять экспозицию.
- Смена экспозиции — изменение поведения: это MINOR (1.6.0), не патч.

**Что сделать в сессии.** Замерить токены декларации; решить, нужен ли
`prepareLoadout`-переключатель; реализовать; добавить тест, который проверяет, что
инструмент *не* попадает в активный набор при `codemode`-экспозиции и остаётся
вызываемым через `ctx.executeTool()`; обновить README (раздел про `/alibaba` и
инструмент) и CHANGELOG.

## 2. Картинки: зарегистрировать DashScope image-модели как `type: "image"`

**Что измерено.** В этом каталоге **ноль** image-идентов: поиск
`qwen-image|wan[0-9]|z-image` по `extensions/alibaba.ts` не находит ничего.
Провайдеры регистрируют только chat-модели.

**Что появилось в 1.0.0.** `ModelRuntime.generateImages()` и
`models.generateImages()` в codemode-скриптах, дискриминированные записи
`type: "image"` в `ProviderConfig["models"]` и реализации, регистрируемые рядом:
`images: { "<ImageApi>": { generateImages } }`. Форма записи описана в
`docs/custom-provider.md` («mixed-operation provider»). Плюс `image()` в codemode
умеет прикладывать картинку к результату.

**Зачем это этому расширению.** Пользователь уже платит DashScope и уже
залогинен этим же ключом. Сейчас «сгенерируй картинку» в pi через alibaba
невозможно: ни один провайдер семейства этого не умеет. Это не обвязка, а новая
возможность — единственный пункт фронтира, который добавляет функцию, а не экономит
токены.

**Первый шаг — один бесплатный запрос, и его нельзя делать наугад.** Взять
резолвящийся ключ (auth.json после `/login` или `$DASHSCOPE_API_KEY`) и дёрнуть
список моделей DashScope, чтобы увидеть: (а) какие image-идентификаторы вообще
доступны этому аккаунту, (б) в каком виде они там присутствуют
(chat-совместимый `/compatible-mode/v1/models` их, скорее всего, не показывает —
тогда проверять `GET /api/v1/models` или документацию по конкретному эндпоинту).
Запрос только читает листинг: это не генерация, денег не тратит. **Any поиск с
генерацией картинки — уже платно и требует отдельного разрешения.**

**Что дальше, если листинг подтвердит.**
- Решить, какой `api`-ключ несёт картинки (`"dashscope-images"` и т.п.) и
  реализовать `generateImages(model, context, options)`, вернув base64/URL так, как
  ожидает `AssistantImages` (типы в `pi-ai/dist/types.d.ts`; см. также
  `pi-ai/dist/images-api-registry.d.ts`).
- Не смешивать с `thinkingLevelMap`/`reasoning_effort`-логикой: у image-записи
  полей чата нет вообще, и попытка переиспользовать `buildCloudModels()` для них —
  самый вероятный источник ошибок. Скорее всего нужен отдельный маленький builder.
- Помнить, что с 1.0.0 «supplying `models` replaces that provider's models across
  chat, image, and classifier operations» (`docs/custom-provider.md`): если
  провайдер уже регистрирует chat-список и вы добавляете картинки, их надо добавлять
  в **тот же** список, иначе chat-модели затрутся.
- Публиковать это как MINOR, с отдельным разделом README про цену генерации
  (у DashScope цена за картинку, а не за токены — в каталоге она нигде не
  выражается, и `cost` в записи будет нулевым).
