# Spec: pi 2.0.0 — the pi 1.0.0 frontier

Status: ready for an implementation session (written 2026-10-03, not yet implemented)

Host floor: pi `^1.0.0` (see `docs/adr/0001-drop-pre-1.0.0-hosts.md`)

## Problem Statement

A user of pi who pays for Alibaba (Plan or Cloud) can chat with Alibaba models, but cannot do
two things the pi 1.0.0 host supports for every other provider:

1. **Generate images.** DashScope serves image models, and the user is already authenticated with
   the same key, but this extension registers chat models only. There is no way to reach an image
   model from a `codemode` script, because no provider registers one, and no way to reach one at
   all with `codemode` turned off.
2. **Control how the extra tooling is presented.** The `alibaba_tools` Sidecar is registered
   `direct`, so its declaration rides in every request, even though most turns never need it. The
   host supports moving it into the `codemode` listing instead, but the extension does not offer
   that choice.

Two further problems show up in day-to-day use:

3. **DashScope errors arrive reworded.** Rate limits and backend failures come back as SSE error
   events wrapped in HTTP 200, and the same condition is phrased differently from one response to
   the next. The extension matches on the finished message's text, so a new phrasing becomes a
   non-retried turn.
4. **The package pays for hosts it cannot use.** It supports pi before 1.0.0 with a hand-written
   type exclusion and a dual-host verification ritual, which blocks the union-typed model list and
   the tool-exposure API that the two items above need.

## Solution

Release 2.0.0 requires pi 1.0.0 or newer and adds the host surface this extension was missing:

- **Image models on the Cloud provider.** DashScope's image-generation families
  (`qwen-image-*`, `z-image-*`, `wan*-image`/`wan*-t2i`) are registered as pi image models. They are
  reachable from `codemode` scripts through pi's own `models.generateImages()`, and the extension
  also ships enough of its own surface to use them without `codemode`.
- **A dedicated image tool, `alibaba_image`.** pi's `models.generateImages()` API cannot carry
  generation parameters (only a prompt and reference images), so the extension registers its own
  tool that takes every parameter DashScope accepts, and returns the images both to the model and,
  as structured content, to `codemode` scripts.
- **Configurable tool exposure.** Both Alibaba tools (`alibaba_tools` and `alibaba_image`) default
  to `codemode` exposure and can each be set to `direct`, `deferred`, or off. A system-prompt
  section tells the model that these tools are reachable from `codemode`, and prefers
  `qwen-image-*` for image generation.
- **Structure-based error classification.** Raw provider stream events are captured and classified
  by their contents, and the classification is what pi's retry path sees.

## User Stories

### Image models

1. As a Cloud user, I want the image models my key is authorised for to be registered as pi image
   models, so that `codemode` scripts can list and run them.
2. As a Cloud user, I want the image catalogue to come from Alibaba's own model list, so that new
   image models appear without an extension update.
3. As a Cloud user, I want only models that generate or edit an image from a prompt to be
   registered, so that vertical products (virtual try-on, face chains, word art) do not pollute the
   listing.
4. As a Cloud user, I want each registered image model to report its true input and output
   modalities, so that a text-to-image model is never offered for an edit and vice versa.
5. As a Cloud user, I want image models to use the same key and Domain as my chat models, so that I
   do not configure credentials twice.
6. As a Cloud user, I want a failure to generate an image to arrive as an error result rather than a
   thrown exception, so that a script can report it and move on.
7. As a Cloud user, I want the generated image to reach me as image data, not as a link that
   expires in 24 hours, so that what I see in the session is the image itself.
8. As a Cloud user with `codemode` turned off, I want an image generation path that does not need
   `codemode`, so that I am not required to enable a sandbox tool to draw a picture.
9. As a Plan user, I want the extension to be honest that image models are not registered for Plan,
   so that I do not hunt for a model that is not there.

### The `alibaba_image` tool

10. As a `codemode` user, I want to call `alibaba_image` from a script with a prompt, so that I can
    generate an image in the same script that uses the result.
11. As a `codemode` user, I want the tool to return structured content with the image blocks, so
    that the script can attach them with `image()`.
12. As a `codemode` user, I want to see the image in the script output, so that the model and I both
    see the result.
13. As a model, I want the tool's result to contain image content blocks, so that a direct call
    shows the image without a second step.
14. As a user, I want to choose the model, so that I can trade speed against quality per request.
15. As a user, I want to set the output size, so that I get the aspect ratio I asked for instead of
    whatever the model picks by default.
16. As a user, I want to set the number of images, so that I can ask for variants in one call.
17. As a user, I want to set a seed, so that I can reproduce or iterate on a result.
18. As a user, I want to give a negative prompt, so that I can exclude things I do not want.
19. As a user, I want to toggle the watermark, so that I control whether output is marked.
20. As a user, I want to toggle prompt rewriting, so that I can choose between a richer image and my
    exact wording.
21. As a user, I want to choose the prompt-rewriting mode, so that I can pick the cheaper direct
    rewrite or the agent rewrite where the model supports it.
22. As a user, I want to toggle the model's thinking mode, so that I can trade generation time for
    quality.
23. As a user, I want to pass one to three reference images for an edit, so that I can modify an
    existing image instead of only generating new ones.
24. As a user, I want to be able to save generated images to a path I choose, so that the result
    survives the session and the 24-hour link.
25. As a user, I want saving to be off unless I ask for it, so that the tool does not write files I
    did not request.
26. As a user, I want a clear error when a parameter combination the model rejects is refused, so
    that I can correct it instead of guessing.
27. As a user, I want to be told when a generation failed but the tool returned no image, so that I
    do not silently get nothing.
28. As an operator, I want the tool to spend money only when I call it, so that nothing generates
    images behind my back.

### Reaching images without `codemode`

29. As a user with `codemode` off, I want a slash command that generates an image from a prompt, so
    that I can use the feature without enabling `codemode`.
30. As a user, I want that command to show progress while the model works, so that a 40–60 second
    generation is not a silent hang.
31. As a user, I want to pick which image model the command uses by default, so that I do not repeat
    the model on every call.
32. As a user, I want to override the default model per call, so that one-off requests do not change
    my setting.
33. As a user, I want the same parameters available on the command as in the tool, so that I do not
    have to learn two surfaces.
34. As a user, I want the command to show the image in the transcript, so that I see what I got.
35. As a user, I want `/alibaba` to report the current default image model, so that I can check my
    configuration.

### Tool exposure

36. As a user, I want `alibaba_tools` to default to `codemode` exposure, so that its declaration is
    not in every request.
37. As a user, I want `alibaba_image` to default to `codemode` exposure, for the same reason.
38. As a user, I want to switch either tool to `direct`, so that the model can reach it without
    `codemode`.
39. As a user, I want to switch either tool to `deferred`, so that it is reachable through tool
    search instead of the `codemode` listing.
40. As a user, I want to turn either tool off entirely, so that it costs nothing and is unreachable.
41. As a user, I want both tools grouped under one namespace, so that the `codemode` listing shows
    them together with one description.
42. As a user, I want the namespace to carry longer usage instructions that a script can read, so
    that guidance does not have to fit in the listing.
43. As a user, I want each tool to declare what it does to the outside world, so that a permission
    extension can decide what to confirm.
44. As a `codemode` user, I want the sidecar result as structured content, so that a script can read
    sources and nested calls without parsing text.
45. As a user, I want a system-prompt line when a tool is only reachable from `codemode`, so that the
    model knows it exists without having to open the `codemode` listing.
46. As a user, I want that same system-prompt section to prefer `qwen-image-*` for image generation,
    so that the model does not wander into a family I do not want.
47. As a user, I want image model names to mark the recommended family, so that the preference is
    visible in the model listing as well.

### Stream errors

48. As a user, I want a rate limit that DashScope phrases in a new way to still be retried, so that a
    transient limit does not end my turn.
49. As a user, I want a transient backend failure to still be retried, so that the same condition
    under a new wording does not become a hard error.
50. As a user, I want the retry decision to come from the raw error the provider sent, so that it
    does not depend on how the message was worded.
51. As a user, I want a permanent error never to be retried, so that a misconfiguration fails fast
    instead of looping.
52. As a maintainer, I want the previous text-matching path kept as a fallback, so that a turn whose
    raw event never arrives behaves as it does today.
53. As a maintainer, I want the classification to be a testable function of the raw event, so that
    new phrasings are added as data, not as new branches in the message path.

### Host floor and housekeeping

54. As a maintainer, I want the extension to require pi 1.0.0 or newer, so that it can use the
    union-typed model list and the exposure API directly.
55. As a maintainer, I want the hand-written chat-only exclusion type replaced by the host's own
    chat member, so that there is one definition of a chat model.
56. As a maintainer, I want the persisted model snapshot to keep the image rows this provider owns
    and drop only classifier rows, so that an offline start still registers images.
57. As a maintainer, I want the Sidecar's model picker to keep receiving chat model ids only, so that
    an image model can never be chosen for a chat request.
58. As a maintainer, I want the README's dual-host claim removed, so that the documented host range
    matches the code.
59. As a maintainer, I want the CHANGELOG to say what breaks and why the release is major, so that an
    upgrade decision needs no archaeology.
60. As a maintainer, I want the new configuration keys cleared by `/alibaba → Reset all`, so that
    uninstall leaves nothing behind.

## Implementation Decisions

### Host floor and the model-config type

- The package requires pi `>= 1.0.0`. The dual-host shim is deleted: the chat-only alias becomes the
  chat member of the host's model-config union (`Extract<ProviderModelConfig, { type?: "chat" }>` or
  the locally named equivalent), and the comment explaining why the exclusion form was used is
  removed. Rationale and rejected alternatives are in ADR-0001.
- Neither `ProviderChatModelConfig` nor `ProviderImageModelConfig` is exported from the package root
  (measured 2026-10-03 on two installs), so the local alias stays; only its definition simplifies.

### Image catalogue

- Image models are fetched from the Cloud Domain's native model list with `capabilities=IG`, the
  same endpoint and auth already used for the chat catalogue. This is a **separate fetch** from the
  chat catalogue: the chat fetch deliberately excludes image ids by id pattern, and the Sidecar's
  model picker must keep receiving chat ids only.
- The fetched list is filtered to a curated allow-list of prompt-driven generators and editors:
  text-to-image — `qwen-image-3.0-pro`, `qwen-image-3.0`, `qwen-image-max`, `qwen-image-plus`,
  `qwen-image`, `qwen-image-2.0`, `z-image-turbo`, `wan2.7-image-pro`, `wan2.6-t2i`;
  edit/image-to-image — `qwen-image-3.0-pro`, `qwen-image-3.0`, `qwen-image-edit-max`,
  `qwen-image-edit-plus`, `qwen-image-edit`.
  Vertical and third-party ids (`aitryon*`, `facechain*`, `virtualmodel*`, `wordart*`,
  `qwen-mt-image*`, `kling/*`, `vidu/*`) are never registered.
- Each image entry declares `type: "image"`, `api: "dashscope-images"`, `output: ["image"]`, and
  `input: ["text"]` for generators or `["text", "image"]` for editors. Cost is zero; see Further
  Notes.
- Image entries are registered in the **same** `models` array as the chat entries on the Cloud
  provider, because supplying `models` replaces the provider's models across every operation. The
  provider also registers an `images` implementation keyed by `"dashscope-images"`.
- The Plan provider registers no image models: Plan hosts were not probed, and Plan's catalogue API
  is not known to expose image capabilities.
- Internal separation: the Cloud chat definitions stay in their own variable and remain the only
  input to the Sidecar picker, the fallback-model count, and chat card derivation. Image definitions
  are held separately and merged only at registration and publication time.

### The image generation implementation

- One synchronous DashScope endpoint covers every model on the curated list, measured live on
  2026-10-03:

  ```
  POST https://{Domain}/api/v1/services/aigc/multimodal-generation/generation
  {
    "model": "<id>",
    "input": { "messages": [ { "role": "user", "content": [ { "text": "<prompt>" },
                                                           { "image": "<url|data-url>" } ] } ] },
    "parameters": { "size": "<w>*<h>", "n": 1, "seed": 0, "negative_prompt": "",
                    "watermark": false, "prompt_extend": true,
                    "prompt_extend_mode": "direct", "enable_thinking": true }
  }
  ```

  Response: `output.choices[0].message.content[]` carries `{ "type": "image", "image": "<url>" }`
  items (and possibly text items). The URL is valid for 24 hours, so the implementation downloads
  the image and returns it as an image content block.
- An `input` item containing `{ image: ... }` is what turns a generator call into an edit; editors
  reject a call without 1–3 image items.
- Functions that are pure stay pure and exported: the catalogue-response parser, the curated filter,
  the card builder, the request-body builder, and the response parser. The network, the download, and
  the write are the only impure parts.
- `usage` in the response is heterogeneous across models — `{ image_count, width, height }`,
  `{ image_count, input_tokens, output_tokens, total_tokens, size }`, or
  `{ output_width, output_height, output_image_count, ... }`. Token counts are mapped to pi's usage
  when present; otherwise usage is left unset (see Further Notes).

### The `alibaba_image` tool

- Parameters: `model` (defaults to the configured default image model), `task` (the prompt,
  required), `images` (0–3 references), `size`, `n`, `seed`, `negative_prompt`, `watermark`,
  `prompt_extend`, `prompt_extend_mode`, `enable_thinking`, `save`.
- The tool calls `ctx.modelRegistry.generateImages()` with the resolved model and a context built
  from the prompt and references, passing the remaining parameters through `options.metadata`, which
  the host forwards to the provider implementation unchanged.
- The result carries the image blocks **twice, on purpose**:
  - `content`: a text line plus the image blocks, so a direct caller and the TUI see the image;
  - `structuredContent` matching a declared `outputSchema`, because a `codemode` script receives only
    `structuredContent` (or text) from a nested tool call — image blocks in `content` never reach the
    script. Shape: `{ images: [{ type: "image", data, mimeType }], model, size?, usage? }`.
  Without `outputSchema` the feature does not work from `codemode` at all.
- `generateImages()` never rejects: a provider failure arrives as `stopReason: "error"` with an
  `errorMessage`. The tool turns that into an error result (`isError`) while keeping the structured
  detail, rather than returning an empty success.
- `save`, when given, writes the image bytes to that path. Not given means no write. This is the only
  file-writing behaviour in the extension.
- Annotations: `readOnlyHint: false`, `openWorldHint: true`, `idempotentHint: false`; `destructiveHint`
  is `true` for `alibaba_image` because `save` can overwrite a file, and `false` for the Sidecar.

### Reaching images without `codemode`

- A new subcommand form of the existing `/alibaba` command generates an image: the prompt plus the
  same parameters as the tool. It calls the model registry directly, so it needs no `codemode`, and
  it emits the result as a custom message carrying image content so the TUI shows it.
- Generation takes 6–57 seconds, so the command reports progress and stays cancellable.
- A new configuration key holds the default image model, set from `/alibaba → Image — Default
  model`, and reported in `/alibaba → Status`.

### Tool exposure

- Each of the two tools gets its own configuration value with the same vocabulary:
  `codemode` (default), `direct`, `deferred`, `off`. `off` means the tool is not registered.
- Default `codemode` is a deliberate change for `alibaba_tools`, whose previous behaviour was
  `direct`. The consequence is recorded: with `codemode` off and the exposure left at the default,
  neither tool is reachable, and the only Alibaba generation path is the `/alibaba` subcommand. The
  `/alibaba` menu, the README, and the CHANGELOG all say this; the CHANGELOG states it is a
  breaking change.
- Both tools share one namespace named `alibaba`, with a short description and longer `instructions`
  that a script reads through `describeNamespace()`.
- The Sidecar's result gains a declared `outputSchema` and matching `structuredContent`
  (`{ action, result, sources: [{ url, title?, snippet? }], calls: string[], retries }`), so a
  `codemode` script reads sources without parsing the text.
- A `before_agent_start` handler adds **one** system-prompt section, present only when at least one
  Alibaba tool is registered with `codemode` exposure. It says which tools `codemode` scripts can
  call, and that `qwen-image-*` is preferred for image generation. This is needed because
  `promptSnippet` and `promptGuidelines` are rendered only while a tool is *active*, and `codemode`
  exposure never activates a tool.
- Image model `name`s carry a short marker on the recommended `qwen-image-*` family, because the
  `codemode` model listing shows the model record as-is.

### Stream-error classification

- A `provider_stream_event` handler records the raw parsed event for the current turn, keyed by
  provider and model, and classifies it by structure and content rather than by the finished
  message's wording: HTTP 429, throttling and rate-limit phrasings, 5xx, and the
  `Backend buffer overflow` family. It is notification-only: the handler cannot rewrite the provider
  response.
- The retry decision still enters pi through the finalized assistant message, so the existing
  `message_end` rewriting stays and consults the captured classification when the turn errored with a
  message it would otherwise not recognise. The current text matchers remain as the fallback for
  turns where no raw event was seen.
- Anything not classified as retryable stays not retryable: a permanent error must fail fast rather
  than loop.

### Configuration, state, and documentation

- New configuration keys: the default image model, and each tool's exposure. They live in the same
  config file as the rest, are written atomically, and are cleared by `/alibaba → Reset all`.
- `/alibaba → Status` reports image model count, the default image model, and both tool exposures.
- The README gains an image-generation section (including the price caveat and the `codemode`
  limitation on parameters for pi's own `generateImages()`), an exposure section, and loses the
  dual-host claim.
- The CHANGELOG entry for 2.0.0 states the host-floor break, the exposure default change, and what
  each new surface does.
- `docs/TODO.md` records the deferred classifier and router work, including what would unblock each.

## Testing Decisions

A good test here exercises external behaviour through the modules' own boundaries: a pure function's
input and output, a request body as the server would see it, a result as the caller would receive it.
Tests must not assert on internal call counts, private helpers, or the shape of intermediate state.
The suite is deterministic and offline — no network, no credentials — which the existing tests
already respect.

Test seams, in order of preference, all of them already present in the suite:

1. **Pure exported functions** — the primary seam, used by the Sidecar, model-compatibility and
   duplicate-guard tests. The new pure surfaces (catalogue parser, curated filter, card builder,
   request-body builder, response parser, stream-error classifier, ownership filter) are tested this
   way.
2. **`globalThis.fetch` replaced inside a `try/finally`** — the existing seam for `postSidecar`.
   The image generation call, its download step and its failure paths are tested this way, asserting
   on the request body sent and the result returned.
3. **The extension factory booted in a child process against a fake `ExtensionAPI`** — the seam the
   agent-directory test uses. It is the highest available seam and the only place registration-level
   behaviour can be observed: which providers, tools, commands and handlers the factory registers,
   each tool's exposure, namespace, annotations and `outputSchema`, and what the
   `before_agent_start` handler adds to the prompt options.

No new seams are introduced. The image implementation is reached through the same fake-fetch seam the
Sidecar already uses, and the tool and exposure behaviour through the existing factory-boot harness.

Modules to be tested:

- the new image module (catalogue parsing, curated filter, card building, request building, response
  parsing, generation including download and error paths);
- the image tool and the `/alibaba` subcommand (parameter mapping to `metadata`, structured content,
  `save` on and off, error results);
- the extension factory (registration, exposure values, namespace, annotations, the prompt section);
- the ownership filter that replaces the chat-only filter, and the chat-only view the Sidecar picker
  uses;
- the stream-error classifier and the rewriting path it feeds.

Aside from adding the new test modules, the model-compatibility test module is updated: the function
it pins as chat-only becomes the ownership filter, and its cases gain image rows to keep and
classifier rows to drop, plus a case that the chat-only view still excludes image rows.

## Out of Scope

- **Classifier models.** pi's `ClassifierModel` surface for DashScope is deferred; the reasoning, the
  experiment that would have to precede it, and what would unblock it are in `docs/TODO.md`.
- **Virtual models / a router.** Depends on the classifier above; deferred for the same reason.
- **Video models.** Wan and HappyHorse video models are in the catalogue but pi has no video model
  type.
- **Image models on the Plan provider.** Not probed and not registered.
- **Asynchronous image endpoints.** The `/api/v1/services/aigc/text2image/image-synthesis` and
  `/api/v1/services/aigc/image-generation/generation` async paths and the OpenAI-compatible
  `/compatible-mode/v1/images/generations` path all work but are not used; one synchronous endpoint
  covers the curated list.
- **Changing generation parameters from pi's own `models.generateImages()`.** The host's script API
  accepts a model and a context only; that is not something this extension can change. The dedicated
  tool exists precisely because of it.
- **Hacking the `codemode` tool's own description** through `prepareLoadout` to inject prose. The
  extension's own listing entries and the system-prompt section are the sanctioned channels.
- **A diagnostics viewer for raw provider events.** The capture is used for classification only.
- **Persisting generated images anywhere but an explicitly requested `save` path.**

## Further Notes

- **Everything in the API contracts above was measured live**, on a corporate Cloud key against a
  Beijing Workspace domain, 2026-10-03: the synchronous endpoint for all nine curated text-to-image
  models; `IG` capability listing (63 models); async and OpenAI-compatible endpoints for comparison;
  and `logprobs` availability on compatible-mode chat completions (used for the deferred classifier
  work). Roughly sixteen paid image generations were spent on these probes.
- **Measured latency** for one image, same prompt: `z-image-turbo` 5.9 s, `qwen-image-plus` 6.2 s,
  `qwen-image` 7.6 s, `qwen-image-2.0` 7.0 s, `wan2.6-t2i` 7.7 s, `qwen-image-max` 16.4 s,
  `wan2.7-image-pro` 36.2 s, `qwen-image-3.0` 57 s. Anything user-facing must tolerate a minute.
- **Default output size differs by model**, measured on one identical prompt: `qwen-image-3.0`
  2048×2048, `qwen-image-max` 1664×928, `z-image-turbo` 1536×1024, `wan2.6-t2i` 1280×1280. This is
  the concrete reason `size` must be settable from `codemode`, which is why the dedicated tool keeps
  existing alongside pi's own image API.
- **Image cost is not representable.** pi prices models per token, and DashScope bills images per
  image; some models report token counts and some do not. Image entries therefore declare zero cost,
  usage is mapped only when token counts arrive, and the README says the picker's cost figures do not
  cover image generation.
- **Two traps found while reading the code**, both of which the implementation must handle and the
  tests should pin: the Sidecar's model picker would accept an image id (`isQwenChatId` does not
  exclude `image`), and the persisted-snapshot filter would drop image rows on an offline start.
- **`save` is the one handle not explicitly confirmed** by the operator: it was recommended as
  optional (no `save`, no write) and is included here on that basis. If it is unwanted, drop the
  parameter and record in the README that images generated from `codemode` are not persisted.
- **Issue tracker.** This spec was written to the repository because no issue tracker or triage label
  vocabulary is configured for this project. Publishing it and applying `ready-for-agent` requires
  running `/setup-matt-pocock-skills` first.
