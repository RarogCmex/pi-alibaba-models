# Spec: pi-alibaba-models 2.1.0 — cache warming as a latency mechanism, and honest prices

Status: implemented 2026-10-07 (this file records the decisions as built)

Host floor: pi `^1.0.0` (ADR-0001). Evidence base:
[`docs/notes/2026-10-07-long-session-cache-provider-data-and-options.md`](../notes/2026-10-07-long-session-cache-provider-data-and-options.md)
(provider probes, pi's warmer internals, four months of local telemetry) and
[`docs/notes/2026-10-07-dashscope-cache-ttl-and-warming.md`](../notes/2026-10-07-dashscope-cache-ttl-and-warming.md)
(documented TTL facts).

## Problem statement

Long Cloud sessions stall on cold prefixes. A 150k–220k-token prompt takes **10–17 s when the cache
hits and 57–151 s when it misses**; across the measured window that is 646 cold misses, roughly
8–10 hours of avoidable waiting. Three things stood between us and a fix:

1. **pi's warmer is a money mechanism.** It refreshes only when `p · missCost − warmCost ≥ $0.05`,
   gives up permanently when a timer fires ~5 % of the declared TTL late, and stops 30 min after the
   last real request (60 min while streaming). For a corporate key the dollar gate is the wrong
   question, and the lateness rule is what produced the failures: **10 of 146 warm requests arrived
   after the block had expired and cost 34 CNY — more than the 136 successful warms (31 CNY)**, all
   of them 274–328 s after the previous completion on 73k–593k-token prompts.
2. **Every price we declared was wrong.** `parseApiV1Prices()` matched `/input/i`, which also matches
   `input_token_cache_read`, and kept the last match: 72 of 154 models were priced from a cache row
   (the default `qwen3.8-max-0902` read 1 instead of 12 CNY/M), 43 tiered models were priced from
   their cheapest tier, and cache reads/writes were declared as 0 — so pi's cost totals, pi-debi's
   waste metrics and the warming gate all ran on numbers that were not the bill.
3. **Nobody could see what the cache did.** pi-ai reads
   `usage.input_tokens_details.cache_write_tokens`, a field DashScope never sends; creation tokens
   live in `usage.x_details[].prompt_tokens_details.cache_creation_input_tokens`. So every cache
   write was recorded as ordinary input, and the Sep 23–27 reporting blind spot went unnoticed.

## Decisions

### D1 — This extension owns warming for Cloud models; `promptCache` is the switch

`promptCache` is the only model field pi's cache warmer reads. In the default mode we declare
**nothing**, so pi's warmer reports "cache lifetime unavailable" and stays out of the way, and
`extensions/cache-warm.ts` runs the schedule. Two engines refreshing the same block would only burn
quota, and pi's engine cannot be extended past its caps: `cache_warming_decision` answers for a
refresh pi already scheduled, it never lengthens the 30/60-minute windows.

Modes (`cacheWarm.mode`):

| Mode | Who warms | Notes |
|---|---|---|
| `extension` (default) | this extension | no dollar gate, own horizon, retries instead of giving up |
| `pi` | pi's warmer | declares `promptCache.short = ceil(refresh / 0.9)` so pi's `0.9·ttl` schedule reproduces the interval; our `cache_warming_decision` handler replaces the dollar gate with the same latency rule |
| `off` | nobody | a pause over 5 min always pays a cold prefix |

The Plan provider keeps declaring `{short: 300}`: our replay depends on DashScope's measured TTL and
on the Cloud credential, so Plan stays on pi's warmer.

### D2 — The warm replays the captured request verbatim

A warm is only a warm if the prefix is byte-identical, so the engine captures what pi actually sent:
the payload from `before_provider_request` and the resolved headers (Authorization included) from
`before_provider_headers`, which pi-ai applies before it builds the payload. The replay changes only
the generation cap and streaming: `max_output_tokens|max_tokens = 16`, `stream: false`, `thinking`
dropped on the Anthropic shape (its budget must stay below `max_tokens`). Endpoint paths are the three
suffixes the OpenAI/Anthropic SDKs append to `baseUrl`.

Compaction and branch-summary requests never reach these hooks — pi builds their options without
`onPayload`/`transformHeaders` — which is also why pi's own warmer skips them. Anything that rewrites
the transcript anyway invalidates the engine explicitly (`session_before_compact`,
`session_before_tree`, `session_before_switch`, `session_start`).

Rejected alternative: registering a custom `Provider` with our own `streamSimple`. It would add a
pi-ai dependency and put us in charge of retry, cancellation and event normalization, to gain nothing
the payload replay does not already give.

### D3 — Schedule from the measured TTL, not from a price list

The block lives 300 s and is renewed by a hit (probe C3/C4/C5). Defaults: refresh every **216 s**
(84 s of margin, 17 refreshes/h), keep warming for **4 h** after the last real request, and skip
prompts under **20 000 tokens** — below that a cold start costs seconds, not a minute. Failures
stretch the interval linearly (×2, ×3, ×4) and end the run after four, because a warm that cannot get
through is usually a rate limit and the next real request needs the quota. A warm never overlaps a
real request (`inFlight`), and every timer is `unref`'d.

### D4 — Prices are parsed exactly, then declared per wire shape

`extensions/prices.ts` matches rows by exact `type`, inside one chosen range and one chosen time
band: `Default` when the model has one, else the tier containing `priceTierTokens` (default 128k),
else the widest tier; `standard`/absent time band first, `peak` before `offpeak`. Thinking-mode rows
are a fallback for input and the preference for output (`priceThinkingOutput`, default true — these
are reasoning models and pi runs them with a level). Batch rows are never picked.

`cacheRead`/`cacheWrite` follow what the wire will actually do (`explicitCacheActive`): the
session-cache header on Responses, pi-ai's own `cache_control` injection on the Anthropic shape, our
markers on Completions. Explicit → read `input_token_cache_read`, write
`input_token_cache_creation_5m`; implicit → read `input_token_cache`, write **0**, because an
implicit write is billed as ordinary input (and 0 is also what keeps pi's warming arithmetic honest).

Unit: the catalog bills CNY per million, pi labels `cost.*` as dollars. `costCurrency` defaults to
`cny` — the number a corporate user reconciles against the Bailian console — and `"usd"` converts at
`cnyPerUsd` (default 7.1). Status always says which unit is in force.

### D5 — Cache telemetry from the provider's own fields

`provider_stream_event` carries the raw event, so `cacheFieldsFromStreamEvent` recovers
`cached_tokens`, `cache_creation_input_tokens` and `cache_type` for all three shapes; `message_end`
merges them with pi's normalized usage into one JSON line in `alibaba-cache.jsonl` (turns and warms
alike, capped at ~1.5 MB by trimming to the last 1200 lines). That file feeds
`/alibaba → Cloud — Cache Warming → Cache statistics` and the Status lines, and it is how a returning
reporting blind spot becomes visible instead of silent.

### D6 — Completions models get `cache_control` markers

Chat Completions has no session-cache header, so models whose catalog rows include explicit-cache
prices get up to two `cache_control: {"type":"ephemeral"}` markers injected by
`before_provider_request` (`extensions/cache-control.ts`): one on the last system/developer message
(which is where DashScope serializes tools) and one on the last markable message. Tool results are
never converted to part arrays. Verified live on `kimi-k2.6`, `glm-5.1`, `deepseek-v3.2`:
`cache_creation_input_tokens` on the first request, exactly the same `cached_tokens` on the second.
Gated on the catalog rows, so a family without explicit support is never touched.

### D7 — Declare what the endpoint accepts, per model and per shape

The catalog's `context_window` is not a limit you can send. Measured on 2026-10-07 across 15 models
([`docs/notes/2026-10-07-dashscope-input-caps.md`](../notes/2026-10-07-dashscope-input-caps.md)):

- Completions and Anthropic reject above a per-model cap with `400 Range of input length should be
  [1, N]`. `N` equals `reasoning_max_input_tokens` for qwen3.8-*, `max_input_tokens` for
  `qwen3-30b-a3b`/`MiniMax-M2.1`, and `context_window` for `qwen-plus`/`kimi-k2.6`/`deepseek-v3.2`/
  `glm-5.1` — on those four it is larger than both other fields. No derivation is exact, so the
  measurements are a table and `min(ctx, max_input, reasoning_max_input)` is the fallback (never above
  a measurement in the sample).
- Responses does not reject: it **silently truncates, keeping head and tail and dropping the middle**
  (marker experiment: at 80k sent all three markers were visible, at 160k and 240k only head and tail,
  with `input_tokens` pinned at ~90 000). The documented "~80 % of the context window" measured at
  79.3–80.0 % for qwen3.6/3.7/3.8, 75.5 % for deepseek-v4 — and **~90 000 flat for the qwen3.5
  generation**, 9 % of a 1 M window. Deriving 80 % there would let pi fill a transcript the endpoint
  then hollows out, which is worse than a 400.
- `max_tokens` above `reasoning_max_output_tokens` is rejected while thinking is on (`qwen3-max`:
  `Range of max_tokens should be [1, 32768]` against a catalog `max_output_tokens` of 65 536), so the
  lower ceiling is declared.

Cards therefore carry `resolveContextWindow(id, api, limits, window, {override, responsesGuard})`,
which returns the number **and its source**; `/alibaba → Status` prints both, so a derived cap is
visibly a guess. An explicit `Context Window — Override` wins outright, and `responsesInputGuard:
false` re-declares the full window.

### D9 — Warm only models that actually cache

The catalog's price rows are a machine-readable statement of cache support, so the engine warms a
model only when `explicitCache || implicitRead > 0`, falling back to the family table when a boot was
served from the compatible-mode listing (which carries no rows). Measured per family in
[`docs/notes/2026-10-07-dashscope-cache-families.md`](../notes/2026-10-07-dashscope-cache-families.md):
explicit caching on `glm-5.1`, `kimi-k2.5/k2.6/k2.7-code`, `deepseek-v3.2` (via our markers) and the
qwen3.x line; implicit on `glm-4.6/5.2/5.3`, `kimi-k3`, `deepseek-v4.x`, `MiniMax-M2.1`; none on the
open-weight `qwen3-<size>b` line. The 5-minute TTL renewed on hit was re-measured on Kimi's explicit
block, so a single `refreshSeconds` serves every family. MiniMax caches only above ~4k tokens and
then intermittently (a hit, then a miss 30 s later on the identical prefix — consistent with a
per-replica cache), which is a reason to keep the prompt floor rather than lower it.

### D8 — Deferred, with reasons

- **Adaptive session-cache header ("Auto")**: the arithmetic only favours `disable` for a whole burst
  (N ≤ 6 turns), never for a single request after a gap — switching modes mid-burst pays the 125 %
  creation twice. Warming makes the deterministic header strictly better for latency, so `on`/`off`
  stays a manual choice.
- **Server-side context (`previous_response_id`, 7-day validity)**: pi-ai sends `store: false` and
  rebuilds context every turn; an upstream conversation, not an extension change.
- **PTU (预置吞吐)**: a purchasing decision, not code.
- **Child/fork prefix alignment**: the cache is prefix-scoped, so a child with a byte-identical
  prefix could inherit the parent's block. The change belongs in pi-subagents' fork path; the
  experiment is sketched in the research note (§6.5).

## Verification

Live, 2026-10-07, against the bound Beijing workspace domain:

- **Engine**: one captured request, 60 s refresh → warm #1 created 1 698 tokens, warm #2 reported
  `cached_tokens: 1698, creation: 0` in 2.3 s. Both landed in `alibaba-cache.jsonl`.
- **Prices**: `qwen3.8-max-0902` 12/36 with `cacheRead 1`, `cacheWrite 15` (was 1/36/0/0);
  `qwen3.7-plus` 2/8/0.2/2.5 (≤256k tier at the 128k probe); `qwen3-max` 4/16 (32k–128k tier);
  `glm-5.3` 8/28/2/**0** (implicit only); `deepseek-v4.1-flash` 2/8 (peak band); `qwen-plus` output 8
  (thinking row); `qwen3-235b-a22b-thinking-2507` 2/20 from thinking rows alone.
- **Markers**: `kimi-k2.6` on Completions — 2 markers injected through the real hook, provider
  returned `creation 1332` then `cached 1332`.
- **Mode `pi`**: card declares `promptCache {short: 240}` (pi schedules at 216 s) and
  `cache_warming_decision` turns pi's `stop` into `warm` for a 150k-token prompt.
- **Families** (`docs/notes/2026-10-07-dashscope-cache-families.md`, run twice with identical
  results): explicit blocks via markers on `glm-5.1` (1921), `kimi-k2.5` (1775), `kimi-k2.7-code`
  (1820), `deepseek-v3.2` (1905); implicit hits on `glm-5.3`/`glm-4.6`/`deepseek-v4.1-flash` (1792),
  `kimi-k3`/`deepseek-v4-pro` (1024, 1024-token quanta); `glm-5.3` identical with the header
  `enable` and `disable`; `kimi-k2.5` TTL — create, hit at +25 s, hit at +4.7 min, expired and
  re-created 5.3 min after that hit. Anthropic shape: markers create explicit blocks for
  `qwen3.8-max-0902` (2084) and `kimi-k2.6` (1820), are ignored by `glm-5.3`, and implicit caching
  runs with or without them.
- **Caps** (re-run of the committed probe after the change): `glm-5.1` 202 745 on both rejecting
  shapes, `qwen3-max` 258 048 on both and `max_tokens` 65 536 → `400 [1, 32768]`; declared windows
  across the catalog now read 792 945 (qwen3.8-max-0902, Responses), 983 616 (same model,
  Completions), 90 000 (qwen3.5-plus/-27b/-35b-a3b, Responses), 89 127 (qwen3.5-flash), 754 977
  (deepseek-v4.1-flash), 780 000 (glm-5.2/glm-5.3/kimi-k3, derived), 1 000 000 (glm-5.3 and kimi-k3
  on the request shapes, where the window binds over a larger cap).
- Unit: 270 tests (`npm test`), `tsc --noEmit` clean.
